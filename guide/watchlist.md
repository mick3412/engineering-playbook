# 待試與複查清單

> 由 `python3 pb.py build` 產生。`pb.py review` 會依日期和實戰紀錄提出建議。

## 待試與爭議的做法

| 代號 | 狀態 | 要點 | 複查條件 | 測試方法 |
|---|---|---|---|---|
| S2-03 | 待試 | 做 agent：先寫死規則，只在需要理解語言的地方用 AI | 下一支走到 2.1 方案比較 的作品 | 何時：下一支走到 2.1 方案比較 的作品｜怎麼做：做 agent 時先寫死規則，只在理解語言處用 AI｜看什麼：錯誤率、成本｜有效＝錯誤和成本都比全 AI 版低 |
| S5-04 | 待試 | agent 的測試矩陣：缺資料、衝突、重複事件、工具失敗、政策邊界、注入、退訂 | 下一支走到 5.1 測試 的作品 | 何時：下一支走到 5.1 測試 的作品｜怎麼做：agent 上線前跑測試矩陣（缺資料、衝突、重複、工具失敗、政策、注入、退訂）｜看什麼：發現的問題數｜有效＝上線後沒有矩陣內的問題 |
| CO-03 | 待試 | 一個 agent 負責一塊工作，不是一件事 | 下一件相關作品 | 何時：下一件相關作品｜怎麼做：一個 agent 負責一整塊工作｜看什麼：交接次數、重工｜有效＝重工變少 |
| CO-09 | 待試 | 進度看板直接從專案檔推導 | 下一件相關作品 | 何時：下一件相關作品｜怎麼做：進度看板直接從專案檔產生｜看什麼：看板和實際進度是否一致｜有效＝不用手動更新也一致 |
| CO-12 | 待試 | 交代 AI 寫目標不寫步驟，學方法不學口氣 | 下一件相關作品 | 何時：下一件相關作品｜怎麼做：交代 AI 寫目標不寫步驟｜看什麼：來回次數｜有效＝比寫步驟時少 |
| CO-13 | 待試 | 省用量的可信做法：一個任務一段對話、要求一次講完、素材先瘦身 | 下一件相關作品 | 何時：下一件相關作品｜怎麼做：一個任務一段對話、要求一次講完、素材先瘦身｜看什麼：用量｜有效＝同類任務用量下降 |
| CO-14 | 待試 | 收尾時不開新方向；待決事項用固定標籤，只列新的或有變動的 | 下一件相關作品 | 何時：下一件相關作品｜怎麼做：收尾時照固定標籤列待決事項｜看什麼：負責人決策花的時間｜有效＝一次決定完 |
| S0-01 | 待試 | 新專案一開始就設強約束 | 下一支走到 0.4 專案規則 的作品 | 何時：下一支走到 0.4 專案規則 的作品｜怎麼做：新專案開始就設型別、lint、測試等強約束｜看什麼：之後 agent 引入的錯誤數｜有效＝比沒設約束的專案少 |
| S0-03 | 待試 | 流程和文件的量依需求調整；多寫文件換來可追溯，不會讓成品更好 | 下一支走到 0.2 範圍 的作品 | 何時：下一支走到 0.2 範圍 的作品｜怎麼做：依需求決定文件量，小改不寫長文件｜看什麼：完成時間、可追溯性｜有效＝更快且需要時找得到紀錄 |
| S0-04 | 待試 | 動作分兩類：可還原的直接做並記錄；硬停止的先列待辦，最後一次問 | 下一支走到 0.3 核准點 的作品 | 何時：下一支走到 0.3 核准點 的作品｜怎麼做：一個多步驟任務照兩類動作處理，硬停止最後一次問｜看什麼：中途被打斷的次數、有沒有誤做硬停止｜有效＝只問一次且零誤做 |
| S1-03 | 待試 | 修 bug 先做出回饋迴圈：一個專門在這個 bug 上失敗的檢查 | 下一個難重現的 bug | 何時：下一個不容易重現的 bug｜怎麼做：先做出會失敗的檢查才開始改｜看什麼：從開始到修好的時間、是否一次修對｜有效＝一次修對且有檢查留下來當回歸測試 |
| S1-04 | 待試 | 除錯四階段；修了 3 次還不好就停下來質疑架構 | 下一個修過一次沒修好的 bug | 何時：下一個修過一次沒修好的 bug｜怎麼做：照四階段走並記下每個假設｜看什麼：修補次數、最後的原因是否在第一階段就能找到｜有效＝3 次內修好或及早發現是架構問題 |
| S2-04 | 待試 | 重大決策用五個角度加匿名互評，最後收斂成一個下一步 | 下一支走到 2.1 方案比較 的作品 | 何時：下一支走到 2.1 方案比較 的作品｜怎麼做：下一個重大決策先問要不要用五角度互評，用的話照流程｜看什麼：結論清楚度、token 花費｜有效＝負責人覺得值得 |
| S2-05 | 待試 | 先問清楚再動手：列出假設、擺出多種解讀，一輪問完並附建議 | 下一個需求模糊的任務 | 何時：下一個需求模糊的任務｜怎麼做：先列假設和多種解讀，一輪問完｜看什麼：之後因誤解而重做的次數｜有效＝零次重做 |
| S2-06 | 待試 | 設計時把術語和決定當下寫下來：GLOSSARY.md 與 docs/adr/ | 下一個要設計資料或介面的作品 | 何時：下一個走到 2.2 介面與資料 的作品｜怎麼做：邊設計邊寫 GLOSSARY.md 和 ADR｜看什麼：之後 agent 用錯名詞的次數、重新討論同一決定的次數｜有效＝兩者都減少 |
| S3-01 | 待試 | 外派的判斷：能用程式或抽查驗證的批次工作才外派，主線只驗證 | 下一支走到 3.2 平行與分工 的作品 | 何時：下一支走到 3.2 平行與分工 的作品｜怎麼做：一批可驗證的工作外派給便宜模型，主線抽查｜看什麼：抽查錯誤率、主線上下文用量｜有效＝錯誤率可接受且主線用量下降 |
| S3-02 | 待試 | 派任務寫交接單；審查只回 PASS 或 FAIL，重試 3 次不過就停下回報 | 下一支走到 3.2 平行與分工 的作品 | 何時：下一支走到 3.2 平行與分工 的作品｜怎麼做：派任務寫交接單，審查只回 PASS／FAIL，最多重試 3 次｜看什麼：子代理一次做對的比例｜有效＝比沒交接單時高 |
| S4-09 | 待試 | 能不寫就不寫：照順序選第一個行得通的做法 | 下一個新功能 | 何時：下一個新功能｜怎麼做：照順序問一遍再動手，記下選了第幾層｜看什麼：新增行數、新依賴數、審查意見｜有效＝沒有新增不必要的依賴，審查沒有「這行不需要」 |
| S6-02 | 待試 | hook 擋下 agent 時，理由裡寫替代做法 | 下一支走到 6.3 規則化 的作品 | 何時：下一支走到 6.3 規則化 的作品｜怎麼做：寫一個 hook，擋下時附替代做法｜看什麼：agent 被擋後是否自己改正｜有效＝不用人介入就改正 |
| S6-03 | 待試 | 收到審查意見：讀完、重述、查證、判斷，再一項一項改 | 下一次收到審查意見 | 何時：下一次收到審查意見｜怎麼做：照五步處理並記下每項的判斷｜看什麼：改完後是否引入新問題、是否有反駁成立的項目｜有效＝沒有因照改而產生新問題 |
| S7-03 | 待試 | agent 上線前：先跑影子模式，再開有限的真實動作 | 下一支走到 7.2 上線檢查 的作品 | 何時：下一支走到 7.2 上線檢查 的作品｜怎麼做：agent 先跑影子模式再開有限真實動作，並寫明備援和負責人｜看什麼：影子期間的錯誤｜有效＝影子期零嚴重錯誤才開放 |
| S8-02 | 待試 | 回顧時改善 agent 的環境：指路說明、自動檢查、審查規則 | 下一個作品完成時 | 何時：下一個作品完成時｜怎麼做：照五類找改進點並實際改一項｜看什麼：下一次同類任務是否少出同樣的錯｜有效＝同樣的錯沒再出現 |
| S0-05 | 待試 | 需求很長時用聽寫口述，再讓工具清成一段乾淨的指示 | 聽寫比較組 P11 測完後 | 何時：下一個需求較長的任務｜怎麼做：用聽寫交代需求｜看什麼：agent 追問的次數｜有效＝追問比打字交代少 |

## 待試與待查的工具

| 代號 | 工具 | 狀態 | 何時用 | 複查條件 | 測試方法 |
|---|---|---|---|---|---|
| T-10 | llm-council 技能 | 待試 | 重要決策想要其他模型的意見時。很耗 token，用前先問負責人 | 重要決策想要第二意見時 | 何時：重要決策要其他模型意見｜怎麼做：先問負責人，同意後跑一次｜看什麼：意見是否改變決策、花費｜有效＝負責人覺得值得 |
| T-21 | Graphify | 待試 | 要讓 agent 理解大型程式碼庫時 | 接手大型程式碼庫時 | 何時：接手大型程式碼庫｜怎麼做：建知識圖譜後問 5 個問題｜看什麼：答案正確率｜有效＝比直接搜尋準 |
| T-30 | task-observer（rebelytics） | 待試 | 想讓技能和手冊從實際修正中持續改進時 | 下一個作品完成做 8.2 時 | 何時：連續兩個作品｜怎麼做：開著它工作，作品完成時看觀察紀錄｜看什麼：建議中有幾條被採用進手冊或技能｜有效＝至少 2 條被採用 |
| T-32 | context-mode | 待查 | 長任務中工具輸出塞爆 context 時 | 2026-12-10 或長任務常塞爆 context 時 | 何時：確認授權後的下一個長任務｜怎麼做：開著它跑｜看什麼：context 用量、是否漏掉該看的輸出｜有效＝用量明顯下降且沒漏資訊 |
| T-34 | agent-browser（Vercel Labs） | 待試 | 要讓 agent 實際開頁面、填表單、截圖來驗證時；和已安裝的 Playwright MCP（T-06）比，看哪個步驟少、結果穩 | 瀏覽器自動化比較組 E5 測試時 | 何時：桌上試驗｜怎麼做：同一個本機頁面，用它和 Playwright MCP 各跑一次「開頁、填表、送出、截圖」｜看什麼：指令數、耗時、失敗率｜有效＝步驟更少且一樣穩 |
